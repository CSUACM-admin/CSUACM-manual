>这篇文章将主要叙述参与手册内容编写的过程．请您在撰稿或者修正页面以前，仔细阅读以下内容，以帮助您完成更高质量的内容。本章的内容参考了：[如何参与 - OI Wiki](https://oi-wiki.org/intro/htc/)

## 前期准备

首先您需要：
- 一个 Github 账号（可以前往 [GitHub 的账号注册页面](https://github.com/signup) 注册）
- 一点点对 Git 的知识（能了解并操作如下指令：`init`, `commit`, `remote`, `clone`, `pull`, `push`, `branch`） 
- 一点点对 Github 的知识（了解 Fork，Pull Request）

还不是很清晰？也没问题！您可以随时通过与您的生成式大模型交互来查缺补漏，或者将本页面丢给大模型让他手把手教你。在您的更改被管理员合并到主仓库之前，您作出的修改均不会出现在主页面上，所以无需担心您的任何操作会破坏正在显示的内容。所以大胆做！

## 操作过程

本项目基于 Astro 框架开发，托管于 Github 仓库 [https://github.com/CSUACM-admin/CSUACM-manual](https://github.com/CSUACM-admin/CSUACM-manual) 中，通过 GitHub Actions 将构建产物推送到 [GitHub Pages](https://csuacm-admin.github.io/CSUACM-manual/)，实现了自动化的持续部署。

因此，参与本项目的流程如下：

1. 将[主仓库](https://github.com/CSUACM-admin/CSUACM-manual) Fork 到自己的仓库中；
2. 将 Fork 后的分支仓库，克隆（clone）到本地；
3. 在本地进行修改后提交（commit）这些更改；
4. 将这些更改推送（push）到你克隆的分支仓库；
5. 提交 Pull Request 至[主仓库](https://github.com/CSUACM-admin/CSUACM-manual) ；
6. 管理员对您的 Pull Request 进行 Review 后，将与您交流并提出意见，待通过后，将会被合并到主仓库中。

## Commit 信息格式规范

对于提交时需要填写的 commit 信息，请遵守以下几点基本要求：

- commit 摘要与正文是在同一个消息输入框内通过换行和空行来区分的；
- commit 摘要请简要描述这一次 commit 改动的内容，请不要过长，以免影响阅读体验；
- 如果需要进一步描述本次 commit 内容，请在正文中详细说明。

对于 commit 摘要，推荐按照如下格式书写：

```txt
<修改类型>(<文件名>): <修改的内容>
```

修改类型分为如下几类：

- feat：用于添加内容的情况．
- fix：用于修正现有内容错误的情况．
- refactor：用于对一个页面进行重构（较大规模的更改）的情况．
- revert：用于回退之前更改的情况．

## Pull Request 信息格式规范

对于 Pull Request，请遵守以下几点要求：

1. 标题请写明本次 PR 的目的（做了什么工作，修复了什么问题）。
2. 内容请简要叙述修改的内容．如果修复了一个 issue 的问题，请在内容中添加 fix #xxxx 字段，其中 xxxx 代表 issue 的编号。

对于 Pull Request 的标题，推荐使用如下格式书写：

```txt
<修改类型>(<文件名>): <修改的内容> (<对应 issue 的编号>)
```

修改类型分为如下几类：

- feat：用于添加内容的情况．
- fix：用于修正现有内容错误的情况．
- refactor：用于对一个页面进行重构（较大规模的更改）的情况．
- revert：用于回退之前更改的情况．

示例：

- `fix(02-contest-introduction/index)`: 修改ICPC（国际大学生程序设计竞赛）的说明
- `feat(00-intro/acm-dream)`: 添加新页面：What is your dream about ACM?
- `refactor(06-growth/index)`: 大幅重构页面结构与内容

## 提交 Pull Request 之后

1. 在收到一个新的 Pull Request 之后，GitHub 会给 reviewer 发送邮件；
2. reviewer 可能会发现问题，并提出 review 或 suggested changes（建议更改，显示为灰色图标）/requested changes（强制更改，显示为红色图标，只会在 reviewer 拥有 repo 写权限时出现）．一般来说，reviewer 也会附上建议和需要进行的更改，在这时，您将会需要继续向 Pull Request 追加其他更改；
3. 在足够多 reviewer 投票通过一个 PR 之后，这个 PR 才可以合并到 main 分支中；
4. 在合并到 main 分支之后，GitHub Actions 会重新构建一遍网站内容，并更新 Github Page。
